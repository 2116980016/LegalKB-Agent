# 设计取舍（ADR）

> 面试里最容易被问倒的不是"你用了什么"，而是"为什么不用另一个"。
> 这里每条都写：选项 → 选择 → 理由 → 代价。

## ADR-1 不用 LangChain，自己做薄封装

- **选项**：LangChain / LlamaIndex / 自己写。
- **选择**：自己写 ~800 行（BM25、RRF、重排、引用解析、评测）。
- **理由**：RAG 的核心只有四件事——切块、召回、融合、引用；框架能省 200 行，但会带来三个问题：
  1. 版本不稳定（`langchain_classic` / `langchain_community` 的迁移成本）；
  2. 出错时栈很深，定位延迟和错误来源困难；
  3. 面试官无法判断你是"会调包"还是"懂原理"。
- **代价**：没有现成的 DocumentLoader / TextSplitter 生态，PDF、Word 需要自己接。
- **反面意见**：如果团队已有 LangChain 基建，跟着用更划算——所以 `LawAgent-Pro` 里我仍保留了 LangChain 版本，两个实现可以对照。

## ADR-2 父子切块，并承认它在本语料上退化了

- **选项**：固定 500/50 切块 / 按段落 / 父子切块。
- **选择**：父块=整条法条，子块≈300 字滑窗。
- **理由**：法律条文常常"前半句是条件、后半句是后果"，切碎会让模型只看到半句。
- **实测**：本语料单条平均 86.6 字，**父子切块退化为 1:1**（1265 子块 / 1260 父块）。
- **结论**：这个设计在本数据集上不产生收益，但对长文档（合同、判决书、设备手册）是必需的；
  参数 `CHILD_SIZE` 可调，换语料即可生效。**把负结果写出来，比假装它有用更可信。**

## ADR-3 混合检索用加权 RRF，而不是分数加权平均

- **选项**：分数归一化后加权 / RRF / 学习一个融合模型。
- **选择**：RRF（k=60，权重 0.5/0.5）。
- **理由**：向量相似度与 BM25 分量纲不同，直接加权需要归一化，而归一化本身依赖分布假设；
  RRF 只用排名，天然可比，且对异常分数鲁棒。
- **代价**：丢掉了"分数差距"的信息（第 1 名 0.9 和第 2 名 0.89 被视为一样）。
- **实测结论（同一套题、两种 embedding，结论相反）**：
  | 策略 | 哈希字面向量 R@3 | bge 语义向量 R@3 |
  |---|---:|---:|
  | vector | 66.7% | **100%** |
  | bm25 | 83.3% | 83.3% |
  | hybrid | 75.0% | 91.7% |
  | hybrid + 词面重排 | 75.0% | 83.3% |
  哈希向量与 BM25 同源（都是 n-gram 统计），融合没有互补信息，反而稀释 BM25；
  换成语义向量后向量支路单独就打到 100%，融合反而因为**把 BM25 的噪声候选带进来**而下降。
  更关键的是：**在语义检索之上叠"词面重排"会掉 16.7 个点**——词面覆盖率会把"语义对但用词不同"的
  正确结果压下去。所以默认 `RERANKER=none`，要用重排就上 cross-encoder，别用词面技巧。
  这条负结果直接写进了 README，因为它比"混合检索提升 X%"更有信息量。

## ADR-4 默认离线（hash embedding + echo LLM）

- **选项**：默认接真实 API / 默认离线。
- **选择**：默认离线，配置后接真实模型。
- **理由**：
  1. 别人 clone 下来 `docker compose up` 就能用，不需要申请 Key（简历项目的转化率取决于此）；
  2. CI 不能依赖外部 API（不稳定、要付费、会泄露 Key）；
  3. 用确定性实现，测试可以断言具体结果。
- **代价**：离线数值不能代表真实效果，所以 README 里明确标注了"离线基线"，生成侧指标标 N/A。

## ADR-5 评测集用「证据锚点」而不是 chunk id

- **选项**：gold chunk id / gold 答案文本 / 证据锚点（原文中的稳定短语）。
- **选择**：锚点（如 `["第585条", "三年"]`）。
- **理由**：chunk id 依赖切块参数，改一次参数整个评测集就失效；锚点是原文里的稳定串，
  即使换切块策略、换 embedding、换向量库，评测集仍然可用。
- **代价**：锚点需要人工挑，且只能验证"证据是否被召回"，不能验证"答案是否完整"；
  后者要真实 LLM + LLM-as-judge（Roadmap）。

## ADR-6 索引用 numpy，而不是一上来就 Milvus/Qdrant

- **选项**：FAISS / Qdrant / pgvector / numpy。
- **选择**：numpy 精确检索（`IndexFlatIP` 等价物），FAISS 作为可选后端。
- **理由**：1265 条 × 512 维 ≈ 2.6MB，矩阵乘法 <1ms；引入向量库只会增加运维成本。
- **切换阈值**：>10 万块或 QPS >50 时换 FAISS IVF/HNSW 或 Qdrant（接口已抽象成 `search(q, k)`）。
